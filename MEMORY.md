A 409 now fails the run, which is the honest outcome since versions are immutable. It also pushes the exact file read from `<PackageId>` instead of a `./nupkgs/*.nupkg` glob, after asserting exactly one `.nupkg` exists. **`PackageId` never matches the folder name** (`Core.Cache` → `CoreSystem.Cache`), so never derive the filename from the tag prefix.

## Decisions and rationale

- **In-project deps are `ProjectReference`, cross-repo are `PackageReference`.** All three cache packages ship from here, so building them from source is right; the CoreSystem.* packages are separately published so they must come from NuGet. csproj edits and `packages.lock.json` must move in the **same commit** or `RestoreLockedMode` breaks restore.
- **`UseLocalProjectReferences` no longer affects the reference graph.** The conditional `ProjectReference` groups in `Core.Cache.Redis.csproj` and `Core.Cache.Rehydration.csproj` duplicated unconditional ones and were removed (Oct 2026). Verified: `dotnet msbuild -getItem:ProjectReference` returns the same single reference with the switch on and off. Its only remaining effect is disabling `RestorePackagesWithLockFile` and `RestoreLockedMode` locally.
- **Quality gates are on** (Oct 2026): `TreatWarningsAsErrors`, `EnforceCodeStyleInBuild`, `AnalysisLevel=latest-recommended`, `Deterministic`, `NuGetAudit`, `NuGetAuditMode=all`. `src/` requires XML docs on every public member and the generated file is packed into the `.nupkg`; `tests/` opts out of docs and of CA1707. CA1716 and CA1711 are suppressed with justifications because both fixes break published 2.x API.
- **The vulnerability gate is `restore`, not a `dotnet list` step.** `dotnet list package --vulnerable` exits 0 even when it prints a High advisory, in both text and `--format json` — so `continue-on-error: true` on that step was removing nothing. What actually blocks is `NuGetAudit` raising NU1902/NU1903, which `TreatWarningsAsErrors` (already on) turns into a restore failure. `NuGetAuditMode=all` is needed because the default audits **direct dependencies only**, so a transitive advisory never becomes a warning. Verified by adding a vulnerable package: NU1004 masks it until you run `--force-evaluate`, then all seven projects fail.
- `InternalsVisibleTo` from `Core.Cache` to the sibling providers and all four test projects is intentional — that is how the tests reach `internal` members.
- Integration tests use Testcontainers, so they need a running Docker daemon. Unit tests do not.
- **`dependabot.yml` is configured for two ecosystems** (`nuget` and `github-actions`, both at `/`). Every NuGet PR it opens arrives failing restore with NU1004, because it edits `Directory.Packages.props` without regenerating the lock files. Verified by simulating a bump. Fix: `dotnet restore CoreSystem.Cache.sln --use-lock-file --force-evaluate`, commit lock files with the bump.
- **Action majors verified against the GitHub releases API (Oct 2026):** `checkout@v7`, `setup-dotnet@v6`, `setup-python@v7`, `upload-pages-artifact@v5`, `deploy-pages@v5`, `NuGet/login@v1`, `codeql-action@v4`. `checkout@v5`+ moved to node24, which is what silenced the Node 20 deprecation warning `@v4` printed on every run. Do not guess these; query the releases API.
- **`CacheOptions.MaxCacheableSize` was removed** (Oct 2026). It was dead from birth: `git log --all -S MaxCacheableSize --pickaxe-regex -- "*.cs"` returns only the standalone-repo migration commit, so nothing ever read it. That forced the major, and it shipped as **3.0.0** (core only) then **3.0.1**. The stale "reserved and not enforced" wording it used to sit next to is gone from `Core.Cache.csproj`.
- `codeql.yml` uses `build-mode: none` for C#, which is officially supported and verified working here. The `Run manual build steps` step never executes and is the documented fallback.

- Consider whether a re-run of a partially completed release should be resumable now that `--skip-duplicate` is gone. Publishing base-first means a failure in the third tag leaves the first two live; re-running those tags will now 409 and fail. That is correct behaviour, but the recovery path is manual.

## Gotchas

- **MSBuild silently collapses a duplicated `ProjectReference`.** With `UseLocalProjectReferences=true` the two identical `ProjectReference` items both reached evaluation, and `-getItem:ProjectReference` listed the same path twice rather than erroring. That is why the duplication went unnoticed: it never broke a build, it only misdescribed what the csproj did. Do not rely on MSBuild to catch a repeated item.
- **Stale `obj/` can fake a NU1004 that no longer exists.** After an experiment that regenerated the lock files, `git checkout` on the lock files was not enough: `dotnet build` still failed NU1004 pointing at a dependency that was no longer in the csproj, because `obj/project.assets.json` still held the old graph. Deleting every `obj/` and `bin/` fixed it. When NU1004 names a package that is not in the csproj, the lock files are probably innocent — check `obj/` first.
- **A failed restore under `RestoreLockedMode` rewrites `packages.lock.json` with empty entries instead of leaving it alone.** A restore that fails with NU1004 leaves the committed lock files gutted, and every later restore then fails for the same reason. If restore starts failing with "target frameworks of the project differ", run `git checkout -- 'src/*/packages.lock.json'` before investigating anything else.
- **`mkdocs build --strict` does not report unbalanced code fences.** Count ``` occurrences per file instead. An unpaired fence shipped once and passed CI.
- Scans for U+FFFD will not find CP850 mojibake. `ÔÜí` in place of `⚡` means UTF-8 content passed through a DOS OEM codepage; look for `[À-ÿ]` clusters. That corruption is **lossy** for emoji outside the Basic Multilingual Plane, so those files must be rewritten, not repaired.
- **The console output codepage here is `ibm850` (cp 850), so any check that reads UTF-8 back through PowerShell is unreliable.** `gh pr view --json body` writes UTF-8 to stdout and PowerShell decodes it as cp850; `í` (C3 AD) arrives as `Ã­`. This is worse than a missed finding, because it manufactures one: an emoji reported as a Spanish accent, and an innocent clean scan reporting false corruption. Every byte-level check must go through a raw path — `cmd /c "gh api ... --jq .body > file.txt"` and then `[System.IO.File]::ReadAllBytes` with an explicit UTF8 `GetString` — and never through `ConvertFrom-Json` on captured stdout. Diagnose the encoding before blaming the regex; I blamed the regex for one round on this and was wrong.
- **Never pipe a file containing emoji through PowerShell into `gh --body-file -`.** The pipeline re-encodes and silently drops every non-ASCII character, so the edit *succeeds* and deletes `🔄 ⚡ ✅ ❌` from the body. `gh pr edit --body-file <path>` reads the file as bytes and is correct. Verify an edit by re-reading it byte-accurately, not by assuming the command worked.
- All `.cs` files carry a UTF-8 BOM and `dotnet format` preserves it. Do not strip it or churn line endings. `.gitattributes` **now exists** (added Oct 2026): it keeps LF in the index and restores CRLF on checkout, and adding it caused no renormalization. Match whatever the file already does rather than normalising.
- `docs/` nav must list a page for it to be reachable, and a nav entry pointing at a missing file aborts the deploy.
- There is no `Behaviors\` folder anywhere and never was on this branch (`git log` over that path is empty). The `<Compile Remove="Behaviors\**" />` exclusion in `Core.Cache.UnitTests.csproj` was scaffolding for an aspect-oriented caching design that was never implemented; it was removed rather than left to rot.
- **Do not trust a nuget.org 404 as proof a package is missing.** In this sandbox, `/v3-flatcontainer/<id>/<version>/<id>.nuspec` and `.nupkg` return 404 for packages that demonstrably exist, including the repo's own long-published 2.0.2. Only `/v3-flatcontainer/<id>/index.json` was reliable, and it lags by several minutes after a publish. The authoritative check is a throwaway `dotnet restore` of a project referencing the package, then read the resolved graph out of `obj/project.assets.json` and the nuspec/XML out of `~/.nuget/packages`.
- `main` is protected: branch, then `gh pr create`. The claim in `AGENTS.md` was inherited from `FEDERIN/CoreSystem` and was **false here until Oct 2026** — verified by API (`protected:false`, no rulesets), not assumed. Note that a push direct to an unprotected `main` succeeds silently rather than failing with GH006, so the stale docs did not fail loudly. `MEMORY.md` carried the same wrong claim until it was fixed.
- **PR titles, bodies and commit messages go in English, even when the conversation is in Spanish.** The user writes in Spanish; the repository is entirely English. That boundary is easy to blur because the whole discussion is in Spanish and a Spanish PR still renders fine. It does not: it stands out against English code, XML docs and READMEs, and it forces the reviewer to switch languages for no benefit. Write the reasoning too, not just the subject. The rule is stated in `AGENTS.md` under CI / branches.
- **A PowerShell pipeline's exit code is not the tool's.** `Select-Object` / `Select-String` / `Out-File` at the end of a `dotnet` command repeatedly reported exit 1 for a successful `mkdocs build --strict` and a successful `git push`. Re-run the command alone, or filter its output, before treating a non-zero code as a failure. This produced two false alarms in one session.
- **A `.ps1` file written as UTF-8 without a BOM is parsed as ANSI by Windows PowerShell 5.1**, which corrupts every emoji before any logic runs. It surfaces as a parse error about a stray token, not as an encoding error, so it is easy to misdiagnose as a syntax mistake. Re-save with `New-Object System.Text.UTF8Encoding $true` and pass `-ExecutionPolicy Bypass` to run it. Prefer editor tools; reach for scripts only for bulk edits.
- **A `\p{So}` regex misses most emoji.** 🏗️ U+1F3D7 is above the Basic Multilingual Plane and arrives as a surrogate pair, so indexing the string never yields its code point; ⏳ U+23F3 and ⏱️ U+23F1 sit outside the usual symbol blocks. A scan built only on `\p{So}` reported 0 of 27 pages decorated when they were. Decode surrogate pairs and widen the range, and print the code points before acting on a finding. The working `Has-Emoji` is in the `docs-accuracy` skill.
- **Bulk string replacement keyed on a separator can silently miss every line.** `GettingStarted.md` uses an em dash (U+2014) where the map had an ASCII hyphen, so 7 headings were left undecorated with no error. Grep the codepoint before assuming the map applied.
- **An uncommitted change you did not make is the user's work, not a leftover.** A local edit to `docs/Why.md` appeared mid-session; it was committed on request rather than overwritten. Check `git branch --contains <sha>` when a verification contradicts reality, because you may be reading the wrong branch.
